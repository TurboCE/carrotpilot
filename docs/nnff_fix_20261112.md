# GM NNFF port and same-input log comparison

Target: `TurboCE/carrotpilot`, branch `nnff_fix`, based on `trailblazer`
`c1dd92951880fe221f59933e1dcf65775b845297`.

## Imported changes

The steering changes from leehyuk1108/carrotpilot `b24e2e6` and `59467c7`
are cherry-picked: GM torque ceiling 300, approximately 33 Hz LKA commands
and default +10/-15 increments for Traverse, Trailblazer, Trailblazer CC and
Trax; full-NNFF low-speed and measured/planned jerk handling. Explicit custom
delta settings still override these defaults. The original incident already
used these settings, so their import is not evidence that it fixes that drive.

The explicit Traverse-to-Trailblazer model substitution and empty-model-search
handling are selectively imported from the same source tree. A donor model is
allowed only when NNFF is explicitly enabled; vehicle and safety parameters
are not substituted. Dedicated steering test fixtures avoid importing unrelated
display/longitudinal changes from the other branch.

The target's longitudinal fixes, physical vehicle model, geometry learning,
indicator behavior and other unrelated features are retained. The separate
auto-hold addition from leehyuk1108 is outside this steering change.

## Remaining NNFF omissions corrected

Compared to FrogPilot `a22c476734514e36b196168cd39743b74f30dc01`:

- Supply calibrated pose before NNFF evaluation, rather than only when
  publishing the already-computed command.
- Use valid live delay for future NN inputs; desired-jerk horizon is delay
  plus 0.1 s. Invalid delay samples retain the previous valid timing.
- Make the full-NNFF friction weight local to each frame, preventing a
  zero-jerk frame from permanently changing later curve response.
- Use FrogPilot conditional integration in an NNFF-only PID; common PID
  behavior is retained for other controllers.
- Refresh applied-torque limiter feedback during AlwaysLateral even when
  `selfdriveState.active` is false. Both incident windows had active lateral
  control and inactive selfdrive state throughout, so the old gate was stale.
- Clear NN history on disengagement and align steering-angle measurement and
  missing-model fallback with the full-NNFF reference.

These corrections use the same existing four-GM full-NNFF scope. Lite retains
its prior behavior. Stored Kp/Ki/Kf, steering ratio and hardware limits are not
changed by this port. There is no curvature-dependent gain scheduling.

This is not a transplant of the entire FrogPilot control pipeline. Target
curvature smoothing/clipping, model-specific smoothing selection, delay
estimation itself, manual-tuning disable/restore behavior and Lite differences
remain outside this change. Matching NNFF calculations does not imply that
different planners, vehicle models or settings produce identical vehicle motion.

## What the original log comparison establishes

The comparison executes the real NNFF controllers, NN weights and PID source.
Schema/Params I/O uses memory adapters. The logged target curvature and vehicle
feedback are held fixed. The original incident vehicle model and manual gains
are shared as controlled inputs to isolate NNFF changes; this is not a replay
of the target branch's complete geometry-learning/planning pipeline.

The Trailblazer NN weights SHA256 is
`2a8dfbfb840e76e4711e59a646dcce7550772b31139c94d06e75edb05b7c5301`.
Incident gains are Kp=1.7, Ki=1.0, Kf=1.2, manual steering ratio=17.6.
The measured source CarParams/learned dynamics and input timestamps are used;
no per-frame integral anchoring is applied after each window's initialization.

Over 19,995 frames, modified NNFF and the pinned FrogPilot NNFF have mean
request difference about `2.16e-7`, maximum `1.40e-6` under these common inputs.

| Incident window | Original → modified request saturation | Original → modified command band RMS |
|---|---:|---:|
| 01:24:05–20 | 51.73% → 51.67% | 0.3294 → 0.3222 |
| 01:37:35–45 | 39.50% → 45.30% | 0.4192 → 0.3603 |

Saturation means `abs(request) >= 0.999`. Band RMS measures 0.4–1.2 Hz command
content after linear detrending with a Hann window. The command band decreases
by about 2.2% and 14.1%, but the second window saturates more. The first window's
command-rate RMS also increases (2.742 → 2.818/s). Improvements are mixed.

The integral/limiter changes also alter normal-window command offsets; one
normal-window mean request difference reaches about 0.307. Hence preservation
of straight-line tracking is not established either. A changed controller is
being compared against **recorded original applied torque**, not against a new
EPS response. That mismatch can freeze integration differently after divergence.

**There is no established closed-loop or road improvement.** A fixed-feedback
replay cannot predict new steering angles, yaw response, lane-center error or
elimination of repeated steering. No validated nonlinear EPS/vehicle plant was
identified for a closed-loop simulation. The apparent command-band reductions
must not be presented as measured reductions in vehicle oscillation.

## Validation and application status

- Six direct NNFF PID tests pass.
- 26 actual-controller/model-selection tests pass with memory schema/I/O
  adapters and the real NN evaluator/weights.
- 42 GM parameter/ramp/low-speed tests pass using actual source via adapters.
- The native CAN controller cases and native Cereal/CarInterface integration
  are not validated in the Termux environment; they remain required checks.
- The branch adds focused native regression tests for those supported runtimes.
- Korean and English settings documentation describes the imported timing,
  torque ceiling and NNFF behavior.

Code publication is separate from vehicle deployment. No vehicle installation,
restart or parameter change was performed in this port. New comparable driving
logs are required to verify straight-line behavior and curve oscillation.
